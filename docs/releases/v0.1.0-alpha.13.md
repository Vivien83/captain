# Captain 0.1.0-alpha.13

Captain's thirteenth public early-access release adds an adaptive delivery
verifier. Captain now distinguishes work that merely ran from outcomes that
have current evidence, performs only the smallest useful correction, and
returns an honest incomplete result when proof cannot be obtained safely.

## Install

macOS, Linux, and VPS:

```bash
curl -fsSL https://github.com/Vivien83/captain/releases/download/v0.1.0-alpha.13/install.sh \
  | CAPTAIN_VERSION=v0.1.0-alpha.13 bash
```

Docker (`linux/amd64` and `linux/arm64`):

```bash
docker pull ghcr.io/vivien83/captain-agent-os:v0.1.0-alpha.13
```

The moving prerelease channel is
`ghcr.io/vivien83/captain-agent-os:alpha`. Pin the immutable version tag for a
reproducible install.

The release contract contains exactly 22 host assets: five platform archives,
five SHA-256 sidecars, five platform manifests, four installers, one aggregate
manifest, and one checksum-bound deterministic provenance statement plus its
sidecar. Host and Docker targets are built locally and strictly one at a time.

## Adaptive delivery verification

- Pure conversation and read-only inspection remain immediate. Captain does
  not add a ceremonial model pass to every answer or after every tool.
- Every effectful tool result receives one ordered, redacted receipt describing
  effect class, evidence strength, scope digest, and status. Raw input, output,
  paths, model drafts, and hidden reasoning never enter this record.
- A successful mutation is not its own post-condition. A relevant inspection
  or check must be newer than the last mutation it covers. Failed effects,
  pending jobs, and uncertain external receipts remain explicit.
- Missing evidence triggers the smallest targeted correction at the next useful
  milestone. Two correction rounds are the hard limit; Captain then reports
  the exact unresolved post-condition instead of looping or claiming success.
- An uncertain external side effect is inspected by identity when possible and
  is never replayed merely to manufacture verification.

## Crash-safe evidence

- Verification starts, corrections, success, incomplete delivery, and
  interrupted work are written through one durable state machine before their
  user-facing phase is emitted.
- A power loss after verification starts produces `verification_interrupted`
  on restart. Captain reassesses current state and never repeats an uncertain
  mutation automatically.
- Project completion, delegated jobs, immutable artifacts, and Live Runs use
  the same receipt policy. An active subject is an inspection, not a completed
  check; terminal status and result identity must be observable.
- Budgets, provider quotas, cancellation, and iteration limits remain
  authoritative. Verification cannot switch models or bypass any guard.

## Verified streaming delivery

Only a response whose existing effect receipts still need correction, force an
incomplete outcome, continue an already-held response, or use a positive
delegation budget enters a bounded fail-closed delivery buffer. Ordinary and
read-only turns continue streaming directly. Every held continuation segment
must match the provider text exactly and contain one terminal event before it
can be released. The held path preserves event order, discards deltas from
failed provider attempts, withholds drafts superseded by a correction, and
emits the final verified or honestly incomplete response exactly once. The
direct path may retry before its first visible delta, but refuses automatic
transport retry after output begins so that a visible prefix is never
duplicated. A disconnected client cannot turn delivery cleanup into an
agent-loop failure.

## Discreet multi-surface progress

- Ratatui, standalone terminal chat, Web Control, Web terminal, and Telegram
  share `verifying`, `correcting`, `verification_verified`, and
  `verification_incomplete` phases.
- The status is transient and does not pollute session history or replay.
- A fast successful verification stays silent. Telegram reuses one Rich card
  only when verification lasts more than three seconds, starts a correction,
  or changes the final delivery to incomplete.
- Cards and status lines contain no tool input, result, path, model draft, or
  hidden reasoning.

## Host update and runtime reliability

- The macOS updater writes the candidate beside the installed binary with
  private permissions, requires ad-hoc signing, executes an exact `--version`
  preflight, syncs the file, and only then performs an atomic replacement.
  Preparation failure leaves the current binary untouched.
- Wasmtime watchdogs are cancelled and joined when execution ends, preventing
  completed calls from retaining engines and delayed Mach exception handlers.
- The active-model quota surface remains provider-reported: compact Chat shows
  provider-wide windows and limits matching the configured model, while other
  model families remain secondary in exhaustive Status and Budget views.

## Certification boundary

The candidate is gated by complete Memory, Runtime, Kernel, API, CLI, Channels,
and cross-surface suites; strict workspace Clippy and all-target checks;
guarded-execution, DOC2, public export, RustSec, browser, power-loss, project
restart, installer, and update smokes. Publication requires every gate to pass
on the final clean source revision. Passing tests certify the covered behavior;
they are not a claim that an alpha is suitable for an unreviewed critical
deployment.

## Local release chain

All host bundles and both Docker architectures are built locally and strictly
one after another with disk and load checkpoints. The host provenance statement
binds release assets to the public source revision, Git tree, `Cargo.lock`,
target, toolchain, profile, and build timestamps. It is checksum-bound but not
independently signed, so Captain claims no SLSA certification level. No paid
GitHub Actions build is required.

## Alpha notice

This is a prerelease. Keep backups and review every installed CapSpec, Skill,
Automation, capability grant, external account, and destructive approval.
Native host processes do not have OS-level isolation, skill prompt scanning is
heuristic, and the host provenance statement is not independently signed.
macOS binaries are ad-hoc signed but not Apple-notarized; the Windows CLI is not
Authenticode-signed. Verify the published SHA-256 sidecar.

Captain binds to loopback by default. For remote access, use the managed-domain
installer or configure authenticated HTTPS yourself; never expose an
unauthenticated daemon directly to the Internet.

The presentation site is deployed separately at `https://captainagent.fr/`.
Its source is intentionally not part of the public Git repository or release.
