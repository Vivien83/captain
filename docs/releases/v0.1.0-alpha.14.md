# Captain 0.1.0-alpha.14

Captain's fourteenth public early-access release introduces one durable Captain
Hub that can be used from lightweight Clients and optional execution Nodes.
Sessions, projects, memory, approvals, and work remain authoritative on the
Hub, while a Node can act on a remote machine without opening an inbound port.

## Install

macOS, Linux, and VPS:

```bash
curl -fsSL https://github.com/Vivien83/captain/releases/download/v0.1.0-alpha.14/install.sh \
  | CAPTAIN_VERSION=v0.1.0-alpha.14 bash
```

Docker (`linux/amd64` and `linux/arm64`):

```bash
docker pull ghcr.io/vivien83/captain-agent-os:v0.1.0-alpha.14
```

The moving prerelease channel is
`ghcr.io/vivien83/captain-agent-os:alpha`. Pin the immutable version tag for a
reproducible install.

The release contract contains exactly 22 host assets: five platform archives,
five SHA-256 sidecars, five platform manifests, four installers, one aggregate
manifest, and one checksum-bound deterministic provenance statement plus its
sidecar. Host and Docker targets are built locally and strictly one at a time.

## One Hub, shared work

- The Hub remains a complete Captain installation with its agent loop,
  providers, memory, sessions, projects, goals, channels, tools, skills,
  automations, audit, Live Runs, and local execution.
- Lightweight terminal, TUI, and Desktop Clients use the same authenticated
  Hub sessions. They do not carry a second provider loop or memory database and
  fail closed instead of silently falling back to a local Captain.
- Client authority covers normal conversational work, sessions, projects,
  workflows, memory, approvals, and cancellable Live Runs. Secrets,
  configuration, install/update, shutdown, device administration, and durable
  approval grants remain operator-only.
- Standalone behavior remains the default composition. Existing local state is
  not migrated into a multi-primary database or replaced by a remote profile.

## Outbound execution Nodes

- A Node pairs to one Hub and opens only an outbound HTTPS 443 connection. It
  prefers authenticated WebSocket and falls back to HTTPS streaming and bounded
  long polling with the same durable protocol.
- Environment or explicit proxies, named proxy-password secrets, `NO_PROXY`,
  and enterprise CA bundles are supported without exposing credentials in
  status, logs, or configuration projections.
- Physical paths stay local. The Hub addresses a logical workspace, and the
  Node repeats path, workspace, tool-family, mutation, approval, and runtime
  guards before every execution.
- `captain node pair/status/run/reset` provide a restartable first operator
  surface. Pairing requests read-only authority unless mutation is explicitly
  requested and separately approved by the Hub.

## Durable pairing and execution

- Enrollment is closed by default, opens for a bounded operator window, and
  closes after restart. One-time display codes, credentials, access tokens, and
  revocation have distinct scopes and lifetimes.
- The Devices registry shows Clients and Nodes with role, state, version,
  capabilities, grants, presence, transport, and actionable offline reasons.
- The wire protocol uses monotonic sequences, durable acknowledgements, leases,
  idempotency keys, local and Hub outboxes, heartbeats, and bounded replay.
- Idle Nodes follow the heartbeat interval negotiated in `Welcome` (15 seconds
  with the current 60-second Hub lease). Long-poll waits are bounded by that
  interval and are not abandoned by the timer. The rail reuses an
  unacknowledged heartbeat and allocates a fresh monotonic sequence only after
  acknowledgement, so inactivity cannot make a live Node appear offline, grow
  duplicate outbox records, or leave a proxy-side receive loop busy.
- A disconnect after a possible effect reports `uncertain` instead of replaying
  it. Exact terminal evidence can reconcile the result later, and an
  idempotent retry cannot execute the same local effect twice.
- `Auto`, Hub, and eligible Nodes are execution targets for sessions and
  projects. A requested unavailable Node fails honestly rather than being
  rewritten as a Hub execution.

## Service readiness

`captain service start` and `captain service restart` now allow a bounded
90-second health window for a real cold boot instead of warning after 12 or 15
seconds. A timeout distinguishes a service manager that is still active from
one that stopped and points to status and logs.

## Dependency security

The terminal stack is upgraded as one compatible set to Ratatui 0.30,
`ratatui-image 11.0.6`, and `ratatui-explorer 0.3.0`. Its only LRU dependency
is fixed `lru 0.18.2`; the stale Windows notification path to vulnerable
`quick-xml 0.37.5` is absent as well. The unfiltered RustSec release audit has
no vulnerability record. Building Captain from source now requires Rust 1.88
or newer; prebuilt bundles do not require a Rust toolchain.

## Certification boundary

The reproducible distributed smoke composes the real API router, public pairing
routes, two Client surfaces, WebSocket transport, durable Hub and Node rails,
the local worker, and guarded file tools. It proves a real mutation and read,
transport loss after mutation, explicit uncertainty, reconnect, exact outbox
delivery, idempotent replay without a second effect, and physical-path
confinement. Network policy tests cover exact HTTPS 443 origins, proxy
precedence, authenticated proxy secrets, transport fallback, and a real
WebSocket upgrade.

Those deterministic loopback tests certify the software composition, not a
particular VPS, DNS zone, reverse proxy, firewall, or certificate chain.
The published release also passed a separate external HTTPS 443 smoke
with a distinct macOS Node and two lightweight terminal Clients. It proved one
real guarded mutation and read, shared-session restoration, a pinned execution
target, lease expiry to an actionable offline state, reconnect beyond a full
lease, exact non-duplicated tool history, and physical-path confinement in API
and Hub-log projections. Operational endpoints, credentials, device/session
identifiers and local paths are deliberately omitted.
Each external deployment must still pass its own HTTPS and Node smoke before
that deployment is described as certified.

## Deferred scope

This release does not add a complete mobile application, local application
connectors, a Telegram machine tunnel, or a multi-primary memory sync. The Node
service is foreground-first; an operator may supervise `captain node run`, but
Captain does not yet install a separate native Node service wrapper.

## Alpha notice

This is a prerelease. Keep backups and review every Client authority, Node
workspace, mutation grant, CapSpec, Skill, Automation, capability, external
account, and destructive approval. A stolen device credential remains usable
until revocation. Native host processes do not have OS-level isolation, and the
host provenance statement is not independently signed. macOS binaries are
ad-hoc signed but not Apple-notarized; the Windows CLI is not
Authenticode-signed. Verify the published SHA-256 sidecar.

Captain binds to loopback by default. For remote access, use the managed-domain
installer or configure authenticated HTTPS yourself; never expose an
unauthenticated daemon directly to the Internet.

The presentation site is deployed separately at `https://captainagent.fr/`.
Its source is intentionally not part of the public Git repository or release.
